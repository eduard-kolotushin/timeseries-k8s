When the baselines worker is enabled, set broker URLs:

  --set baselines.druidBroker=http://druid-broker.druid.svc:8082
  --set baselines.kafkaBrokers=kafka.kafka.svc:9092

The worker runs in its own Deployment ({{ .Release.Name }}-baselines), independent of Grafana. Scale it without touching Grafana:

  kubectl -n {{ .Release.Namespace }} scale deployment/{{ .Release.Name }}-baselines --replicas=N

Replicas divide the metric hashes by rendezvous hashing; no coordinator and no leader. SHARD_ID is each pod's IP (Downward API status.podIP) and SHARD_DNS is the headless Service {{ .Release.Name }}-baselines-headless, whose A records are those same pod IPs. The Service name is deliberately bare, so it resolves through the pod's search domains on any cluster domain. `baselines.membership` (default `dns`) selects the source; `--set baselines.membership=store` reads the Postgres heartbeat instead.

The worker publishes from a stored snapshot and trains on a cron, so its Druid calls are bounded:

  --set baselines.druidMaxRange=24h     # max time range per SQL request (0 = one request)
  --set baselines.druidMaxRps=4         # requests per second against Druid (0 = off)
  --set baselines.trainConcurrency=2    # whole retrains in flight
  --set baselines.hashScanTtl=30m       # cached span scan; publishing re-reads nothing
  --set baselines.defaultRetrainCron='0 3 * * *'

The rest of the worker's knobs are rendered only when set, so an empty value keeps the worker default
(quoted); they reach the pod as LOG_LEVEL, DRUID_TIMEOUT, DRUID_RETRIES, DRUID_MAX_INFLIGHT,
DRUID_AUTH_HEADER, DRUID_AUTH_VALUE, SCAN_RANGE, SNAPSHOT_CACHE_TTL and RETRAIN_RETRY:

  --set baselines.logLevel=debug        # info (default) | debug
  --set baselines.druidTimeout=60s      # default 60s
  --set baselines.druidRetries=2        # default 2; 0 disables retries
  --set baselines.druidMaxInflight=4    # default 4
  --set baselines.druidAuthHeader=Authorization --set baselines.druidAuthValue='Basic <base64>'
  --set baselines.scanRange=48h         # default max(2*lookback, 24h)
  --set baselines.snapshotCacheTtl=60s  # default 60s
  --set baselines.retrainRetry=5m       # claim lease / failed-retrain delay, default 5m

Snapshots, the retrain queue and (with membership=store) the peer set live in Postgres. The worker ConfigMap renders BASELINE_STORE_HOST/PORT/DATABASE/USER/SSLMODE from the same `postgres` values as the plugin snapshot store; the password comes from the {{ .Release.Name }}-store-credentials Secret, which both Deployments `envFrom` (a ConfigMap would print it through `kubectl get configmap -o yaml`). Leave `postgres.url` empty and the worker keeps its per-tick fit path:

  --set postgres.url=overlay-postgres.overlay-postgres.svc:5432
  --set postgres.database=overlay --set postgres.user=overlay --set postgres.password=overlay

`postgres.url` also accepts a DSN (`postgres://user:pass@host:5432/db`): its host and port are used,
while credentials and database still come from `postgres.database`/`user`/`password`. A TLS-required
server is reached with `--set postgres.sslMode=require` (default `disable`), which every render — the
app/Forecast datasource jsonData, the FORECAST_STORE_*/BASELINE_STORE_* env and the Postgres
datasource — takes.

`baselines.storeHost` overrides only the rendered host/port (the credentials and database still come from `postgres.*`), which is how an install reaches the same store by a different DNS name:

  --set baselines.storeHost=overlay-postgres.overlay-postgres.svc

Beware: `--set baselines.membership=store` requires a store. With neither `postgres.url` nor `baselines.storeHost` the worker exits at startup with a configuration error, and the pod CrashLoops — membership `store` is not a fallback to `dns`.

kubectl scale changes the live replica count only; the next helm upgrade resets it to baselines.replicas.

Disable the worker:

  --set baselines.enabled=false

Grafana admin password (Helm default secret):

Port-forward Grafana:

  kubectl port-forward svc/{{ .Release.Name }}-grafana 3000:80

Images must exist before pods can start. Publish both images to GHCR by pushing a v* git tag, or build locally:

  make docker-grafana
  make docker-baselines

A tag is an override, not a delivery channel: `pullPolicy: IfNotPresent` means a node that already
cached a tag keeps serving that copy, so a rebuilt image must be published under a new immutable tag
(a commit sha, or the `vX.Y.Z` release tag) and pointed at explicitly, e.g.
`--set grafana.image.tag=<sha> --set baselines.image.tag=<sha>`. The sibling sandbox does exactly that:
`make helm-images` tags each image with the short sha of the sibling ref its Dockerfile pins and
`make helm-up`/`make helm-refresh` pass those tags here.

A full Kafka + Druid + Prometheus + OpenSearch + overlay Postgres + this chart stack is sibling timeseries-grafana-sandbox `make helm-up`.

The forecast app retrains stored panel snapshots from its own backend on a cron, with no browser open:

  --set grafana.retrainCron='0 3 * * *'                 # omit for the plugin default
  --set grafana.pluginToken=<viewer service-account>    # needed when anonymous auth is off

grafana.pluginToken is provisioned as the app's secureJsonData.grafanaToken, the same path as the snapshot-store password. Without a token the scheduler can still fetch frames from a Grafana that does not require auth for /api/ds/query; a query whose snapshot is due retrains it either way.

Grafana provisions its datasources and the forecast app only at startup and every provisioning file is
mounted with `subPath`, which kubelet never updates in a running pod. Changing `grafana.retrainCron`
or `grafana.pluginToken` therefore rolls the Grafana pod on its own (the Deployment carries a checksum
of those values). A change that only affects the store — `postgres.*` lives outside the Grafana
subchart's value scope, so no checksum can see it — needs an explicit rollout:

  --set grafana.configRevision=$(date +%s)

Grafana's container is also given default requests/limits (2Gi memory) because the plugin's fits run
inside that process; an unbounded forecast window would otherwise consume the node instead of the pod.
